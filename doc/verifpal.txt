*verifpal.txt*   Verifpal support for Neovim: verification, diagnostics, docs

                                                                    *verifpal*
                                                              *verifpal.nvim*

Neovim support for Verifpal <https://verifpal.com>, the symbolic formal
verification tool for cryptographic protocols. Write a protocol model in a
`.vp` file, run the attacker analysis without leaving the editor, and read the
attack it found in the names your model gave the values.

1. REQUIREMENTS                                        *verifpal-requirements*

Neovim 0.12.4 or newer. The plugin drives Verifpal through its language server
and uses |vim.lsp.config()|, |vim.lsp.enable()| and |vim.lsp.foldexpr()|. Older
releases crash in the LSP folding handler when a buffer is formatted on save.

Verifpal 1.1 or newer, for the `lsp` subcommand. Install it from
<https://verifpal.com>.

There is no fallback. Everything this plugin does — highlighting, hover,
completion, diagnostics, folding, formatting, analysis — comes from the
server, so a missing or too-old binary leaves a plain `.vp` buffer rather
than a partly-working one. `:checkhealth verifpal` says which it is.

==============================================================================
2. INSTALLATION                                        *verifpal-installation*

With lazy.nvim: >lua
    { "symbolicsoft/verifpal-nvim", ft = "verifpal" }
<
With the binary somewhere unusual: >lua
    {
      "symbolicsoft/verifpal-nvim",
      ft = "verifpal",
      opts = { path = "/usr/local/bin/verifpal" },
    }
<
`setup()` is optional. Every default works on its own.

==============================================================================
3. THE LANGUAGE SERVER                                          *verifpal-lsp*

Opening a `.vp` file starts `verifpal lsp` and attaches it to the buffer. From
there the usual LSP mappings apply, and nothing here is special:

    K            hover: a primitive's signature, arity, output count, whether
                 it may be checked with `?` and which weakening assumptions it
                 accepts; or, over a constant, who created it, what it was
                 assigned, who knows it and from whom, and its phases
    gd           go to where a constant or principal was declared
    gr           list every occurrence
    grn          rename a constant or principal everywhere
    gO           document symbols: principals, messages, phases, queries
    <C-x><C-o>   completion, or |vim.lsp.completion| if you enable it

Completion is context-aware: query kinds inside `queries[ ... ]`, weakening
assumptions inside a primitive's parameter brackets, qualifiers after `knows`,
primitives and known constants inside a `principal` block.

Highlighting comes from semantic tokens, so it reflects what the parser
decided rather than what a regex guessed. Folding comes from the AST, so a
guarded value (`[ga]`) and a capability parameter (`SIGN[forgeable]`) create
no folds, and a bracket inside a comment closes nothing.

The server is configured for you. To adjust it, use |vim.lsp.config()| with
the name "verifpal" before a `.vp` buffer is opened.

==============================================================================
4. COMMANDS                                                *verifpal-commands*

                                                             *:VerifpalVerify*
:VerifpalVerify [n]     Run the attacker analysis on the current buffer,
                        optionally with `n` sessions per principal. The buffer
                        is analyzed as it stands, unsaved edits included, and
                        nothing is written to your file.

                                                             *:VerifpalCancel*
:VerifpalCancel         Stop the running analysis.

                                                            *:VerifpalResults*
:VerifpalResults        Open the results panel. Verifies first if there is
                        nothing to show. See |verifpal-results|.

                                                              *:VerifpalClear*
:VerifpalClear          Clear this plugin's diagnostics.

                                                             *:VerifpalFormat*
:VerifpalFormat         Reformat the buffer with Verifpal's canonical
                        formatter. |vim.lsp.buf.format()| does the same.

                                                            *:VerifpalDiagram*
:VerifpalDiagram[!]     Show the protocol diagram. With `!`, Verifpal's
                        mermaid `sequenceDiagram` source instead.

                                                            *:VerifpalRestart*
:VerifpalRestart        Stop the language server. It starts again on the next
                        `.vp` buffer. Use after installing a new Verifpal.

                                                               *:VerifpalInfo*
:VerifpalInfo           Report the binary in use, its version, and whether the
                        server is attached.

5. CONFIGURATION                                      *verifpal-configuration*

>lua
    require("verifpal").setup({
      path = "verifpal",        -- binary path, or a name looked up in $PATH
      sessions = nil,           -- nil defers to verifpal's own default of 2
      verify_on_save = false,
      format_on_save = false,
      notify = true,
      panel = { split = "botright", height = 20, focus = true },
    })
<
A misspelled option is reported rather than silently ignored: an option that
quietly does nothing reads as a setting that was applied.

Hovering, completion, folding, indenting and diagnostic severities are no
longer configured here. They are the language server's, and you configure them
the way you configure them for every other language — see |vim.lsp.config()|
and |vim.diagnostic.config()|.

`sessions` is worth knowing about. Session replication costs roughly four
times the work, so `sessions = 1` is the escape hatch for a model too large to
afford the default of two. A query that holds at one session has been checked
against a weaker attacker than a query that holds at two.

==============================================================================
6. DIAGNOSTICS                                          *verifpal-diagnostics*

Two kinds arrive on the same list, and they never coexist.

While you type, the server reports parse and sanity errors on the line and
column that caused them, with the engine's own note and help text, and with
any secondary location attached as related information — a rebound constant
points at both of its assignments.

After an analysis, each query gets a mark on its own line: an error where the
attacker contradicted it, an informational mark where it held. The narrated
attack trace rides in the message, so |vim.diagnostic.open_float()| shows the
whole attack without opening the panel.

A model that does not parse produces no verdicts, and a run that produced
verdicts had no errors, which is why one list is enough.

==============================================================================
7. THE RESULTS PANEL                                        *verifpal-results*

`:VerifpalResults` opens a panel with each query's conclusion and, where the
attacker won, the minimized attack narrated as numbered causal steps: >

    Verifpal — simple.vp
    c1a1  ·  2 sessions  ·  1 ms  ·  2 of 2 contradicted
    ────────────────────

    FAIL  confidentiality? m1
          m1 (m1) is obtained by Attacker.
          1. Attacker constructs PUBKEY(nil) from nil.
          2. Attacker replaces ga (sent by Alice to Bob) with PUBKEY(nil).
          3. Attacker observes e1 on the wire.
          4. Attacker observes gb on the wire.
          5. Attacker constructs gab from gb, nil.
          6. Attacker opens e1 with gab, obtaining m1.
<
The trace is the reason to believe a verdict, and reading it is how a
modelling mistake is told apart from a real attack. `<CR>` on a query jumps to
it in the model; `q` closes the panel.

                                              *verifpal-assumptions*
If the model declares any weakening assumptions — `PUBKEY[weak](a)`,
`SIGN[forgeable](sk, m)`, `ENC[malleable](k, m)` — they are listed at the top
of the panel. A model that declares one is not being analyzed on its own
terms: an attack found under it is genuine only under that assumption, and a
query that holds is conditional on it. Neither is an unconditional result, so
neither is reported as one.

==============================================================================
8. DIAGRAMS                                                 *verifpal-diagram*

`:VerifpalDiagram` shows the protocol as each principal's steps in order, with
the messages between them called out: >

    Alice
        knows public c0
        generates a
        ga = PUBKEY(a)

    Alice ──▶ Bob :  ga

    Bob
        gab = DH_KEX(ga, b)
        e1 = AEAD_ENC(gab, m1, c0)
<
`:VerifpalDiagram!` gives Verifpal's mermaid `sequenceDiagram` source instead.

==============================================================================
9. STATUSLINE                                            *verifpal-statusline*

`require("verifpal").statusline()` returns a spinner while an analysis runs,
the verdict once it has finished, and "" when there is nothing to say. >lua

    vim.o.statusline = "%f %{v:lua.require'verifpal'.statusline()}"
<
==============================================================================
10. LUA API                                                     *verifpal-api*

All of these take an optional buffer number; 0 or nil means the current
buffer.

    require("verifpal").setup(opts)      apply configuration
    require("verifpal").verify(buf, o)   run the analysis; `o.sessions`,
                                         `o.on_done(report)`
    require("verifpal").cancel(buf)      stop it
    require("verifpal").clear(buf)       clear diagnostics
    require("verifpal").report(buf)      the last report, or nil
    require("verifpal").running(buf)     whether an analysis is in flight
    require("verifpal").results(buf)     open the results panel
    require("verifpal").diagram(buf, r)  open the diagram; `r` for mermaid
    require("verifpal").format(buf)      reformat
    require("verifpal").statusline(buf)  a short status string
    require("verifpal").info()           lines describing the binary in use

A report is a table with `code`, `sessions`, `elapsed_ms`, `attacks`,
`assumptions` and `queries`. Each query has `query`, `kind`, `resolved`,
`conclusion`, `trace`, `preconditions`, `line` and `column`.

11. TROUBLESHOOTING                                 *verifpal-troubleshooting*

`:checkhealth verifpal`
        Reports the Neovim version, the binary found, its version, whether it
        has the `lsp` subcommand, and whether the server attached.

Nothing is highlighted, and hover does nothing
        The server did not start. Either Verifpal is not installed, or it
        predates 1.1 and has no `lsp` subcommand. `:VerifpalInfo` says which.

The analysis takes a very long time
        Session replication costs roughly four times the work. Try
        `:VerifpalVerify 1`, or set `sessions = 1`. Some models are genuinely
        slow: a twelve-step ratchet with two dozen queries is a lot of search.

I upgraded Verifpal and nothing changed
        `:VerifpalRestart`, then reopen the buffer.
